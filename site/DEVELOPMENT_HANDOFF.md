# 开发交接：学习台、技术世界树与内容审核

更新：2026-10-12。这是开发说明，不放进读者导航。交接分支为 `codex/study-workspace-chronicle-handoff`，基于已合并的 PR #63 之后的 main（`cb75ff7`）。本次 PR 保存已有进度，供后续共同开发；不是 v1.0.0 发布，也不表示内容已全部验收。

## 这个项目到底想做什么

让想学 AI / ML 的人少花一些找资料的时间。有人只是想弄懂一个概念，有人正在转方向，有人熟悉技术、只需要为面试查漏补缺。三种需求都应该有入口，不要求每个人从头读完整个网站。

这里是免费、公开、可以一起维护的学习笔记，不是公司题库，也不承诺帮人“破解面试”。内容有作者的取舍，也会过时；欢迎读者纠错、补例子和补充其他方向。官方站保持免费，原创代码用 MIT，原创笔记用 CC BY 4.0；第三方材料另看许可，详见 [LICENSE.md](../LICENSE.md)。

把功能分成三个入口，但不要维护三份相同的内容：

| 入口 | 读者来做什么 | 不应该变成什么 |
| --- | --- | --- |
| 知识库 | 查概念、循序学习、看代码和系统取舍 | 只有标题和结论的速记表 |
| 学习台 / 面试准备 | 选练习、安排时间、回到原文、保存自己的记录 | 公司专用题库、打卡排行榜或能力评分 |
| 技术世界树 / 编年史 | 看一个领域怎样发展，哪些方向在何时相遇 | 热门论文列表、产品广告或学习计划界面 |

内容审核是维护者工具，不是第四个面向读者的聊天产品。

## 1. 学习台：先让一个人顺畅地学下去

### 应有的使用过程

选一个方向和起点 → 看练习建议 → 按自己的空闲日期调整时长 → 确认保存 → 打开原文学习 → 留下问题或记录 → 下次继续。

时间是**有效学习时间**，不是倒计时，也不是规定多久应该学会。可以隔几天学一次，每次时长不同。没有连续打卡、落后惩罚或“掌握率”；完成一次安排，不代表掌握了一个主题。

### 实现在哪里

```text
Markdown 原文 ── build.py ── 静态页面 + 可信笔记目录
                              ↑
study-routes.json ── prep_workspace.py ── 路线与练习入口
                              ↓
Dashboard → 路线草稿 → 用户确认 → 统一进度存储
                              ↓
                    日历 / 笔记 / 备份 / 更新提示
```

- 页面：`interview/dashboard.md`、`.en.md`；准备入口仍是 `interview/README.md`、`.en.md`。
- 路线数据：`site/study-routes.json`，练习引用已有笔记，不复制正文。每个练习有稳定 ID，同一篇文章可以对应多个不同练习。
- 静态渲染：`prep_workspace.py`、`prep_schedule.py`、`prep_progress.py`。
- 交互：`static/prep-workspace.js`、`prep-route-planner.js`、`prep-schedule.js`、`prep-calendar.js`。
- 样式：`static/prep-workspace.css`、`prep-schedule.css`、`prep-progress.css`；样式尽量局部生效。

### 不能破坏的数据约定

- 主键保持 `cooking-agi:prep-progress`，备份格式保持 `cooking-agi-prep-progress` / version 1。网站版本、备份版本、内容 edition 是三件事。
- 中文与英文共享稳定笔记 ID。移文件先查 `site/progress-id-overrides.json`，不能让旧记录变成另一篇文章。
- 所有写入走 `prep-progress-store.js` 及共享控制器；不要给每个新功能再建一套 localStorage。
- 导入先预览，未知笔记和兼容的可选字段保留。无法理解的未来格式暂停写入，不覆盖成空记录。
- 更新路线不改用户已经保存的任务。新文章默认只入“待安排”，不填日期，也不清掉学习状态。
- 只有实质内容变化才登记 `site/content-updates.json` 的 revision 和双语摘要。修文案、换布局、调分类不触发“需要重学”。
- git pull 不会主动改浏览器进度，但不同域名、端口、浏览器各有自己的存储。换设备用导出 / 导入；不把私人备份提交到 Git。
- 浏览器恢复副本不是异地备份。配额、清理、隐私模式和真正同时发生的多标签写入都有边界；不能承诺永不丢失。
- 未保存草稿只是当前页面内存，刷新或跨语言导航会丢失；必须明确显示未保存。

详细约定：[STUDY_WORKSPACE.md](STUDY_WORKSPACE.md)、[PREP_PROGRESS.md](PREP_PROGRESS.md)。

## 2. 编年史：需要补的是历史，而不只是节点

### 大树要表达的东西

AI 不只由模型论文构成。算法在变化，支撑它的电力、芯片、存储、网络、操作系统、编译器、数据和评估也在变化。这些方向有自己的历史，不是为了等待 LLM 出现而存在。

先看一个时期的大势，再看当时几个重要变化；对某个领域感兴趣，可以进入小树，按时间读它自己的发展。论文、系统演示、产品发布和基础设施建设要分清，不能混成一种“突破”。

当前十一条主枝：电力与机房、芯片与计算、内存与存储、网络与互连、系统软件、分布式与服务、数学与算法、数据与评估、模型与学习、应用与产品、人/协作/责任。

### 现有内容为什么还不够

- 77 个节点并不均衡：数学与算法只有两个节点；语音、推荐、控制等历史线还很薄。
- 许多正文停留在“某年提出某技术”，没说明以前怎么做、哪里难、这次到底改变了什么。
- 硬件、数据、算法和产品之间只有少量已登记的联系。树枝的视觉相邻不能代替有证据的技术关系。
- 读者容易记住名字，却不一定能说出各个年代的变化。继续加论文名不会自动解决这个问题。

### 下一轮先做这些

1. **重审九段年代导语。** 讲清当时的任务、资源条件、主要做法和变化；承认同期有不同路线，不写成所有技术最终汇入 LLM。
2. **先写扎实几个代表节点。** 可以从 AlexNet、Transformer、AlphaGo、CUDA / GPU 计算、Linux / 分布式系统这些已有节点开始，验证新的讲述方式，而不是一次机械改完 77 篇。
3. **再补断裂的历史线。** 数学与统计/优化、传统 ML、语音、搜索推荐、控制机器人、训练框架、供电与冷却都需继续研究。Shannon、随机逼近、Bellman、感知机、TensorFlow / PyTorch 等只是候选，不是已完成的收录清单。
4. **从具体工作补联系。** 说明哪个系统用了哪个数据集、算法或软件，关系的证据来自哪里；并行发展不自动画成继承关系。
5. **拿读者视角验收。** 不打开来源也能读懂主要变化；想深入时能继续看机制、例子、限制和原始资料。

一个节点的内容应能自然回答：以前怎么做？卡在哪里？它改了哪一步？从一个小例子怎么看出差别？后来怎样被使用？还有什么没有解决？这些是写作检查问题，不要求每一篇都机械套六个小标题。

日期要对准具体事件。论文初稿、会议发表、产品发布、真正交付可能不是同一年。别把一个实验的成功写成全行业采用，也别把近年的尝试写成定论。GRPO 这类已有后续使用的方法可以收录；尚未稳定的后训练做法仍应保留不确定性。

### 数据与交互

```text
technology-tree-data.json
  layers → topics                  领域分类
  eras → branches → works          时间与阅读分组
  nodes                            唯一正文、日期、双语、来源
  connections                      单独核实的跨领域联系
        ↓
technology_chronicle.py → 世界树 + 表格视图 + 可直接读的 HTML 年表
world_tree.py           → 建木式世界树 SVG（宽屏 / 窄屏）
        ↓
悬停联系 / 领域筛选 / 年代高亮（chronicle.js），全部复用同一份正文
```

- 保留 version 3 和稳定 `event-*` / `field-*` ID；新增节点必须有一个按年份排列的规范入口。
- `chronicle.js` 管悬停说明、联系高亮、领域筛选和年代高亮；旧版画布与弹层模块已移除，见 TECHNOLOGY_TREE.md。
- 语言切换、刷新、前进后退应保留正在读的节点；不开 JS 仍能看完整年表和来源。
- 视觉连线、枝条长度、动效不表示技术影响力或历史因果。近期开放问题可用虚线区分，但正文不能变淡到难读。
- 编年史页面不要放内部选材政策、agent 工作流、面试安排或长篇“我们为什么设计这个功能”。维护说明留在 `site/`。

详见 [TECHNOLOGY_TREE.md](TECHNOLOGY_TREE.md)、[CHRONICLE_EVIDENCE.md](CHRONICLE_EVIDENCE.md)、[CHRONICLE_RESEARCH_BACKLOG.md](CHRONICLE_RESEARCH_BACKLOG.md)。

## 3. Multi-agent：先做内容审核，规划以后再接

当前工具在 `site/review_assist.py`：维护者选公开片段 → 技术 / 教学 / 证据与安全三种角色 → 校验原文引句 → 保留各自意见的报告 → 人核实后修改。

默认 dry-run 只生成请求，不调用模型。离线可以导入三角色输出；显式提供模型、凭据和 `--send-public-input` 才会调用付费 API。没有接 GitHub 自动评论，没有给模型浏览器、代码执行、写仓库或发布权限。这轮交接也不启用远端服务。

三份模型意见不等于三位独立专家；零问题不等于审核通过。报告中的引用校验只能证明原句在所给片段中，不能证明技术结论正确。原论文、实际代码和双语语义仍需单独检查。

规划 agent 是另一条未来路线：课程建议 → 时间安排 → 计划检查 → 本地校验 → 用户看 diff 后确认。它不能直接写进度，更不能默认上传私人备注、简历或整份备份。现有手动排期应一直能独立使用。

详见 [REVIEW_ASSIST.md](REVIEW_ASSIST.md)、[AGENT_SYSTEMS.md](AGENT_SYSTEMS.md)。

## 4. 两个人或两个 agent 怎么同时开发

以下是建议分工，不表示已经派发任务。Claude Code 先从本 PR 的 head 创建自己的分支 / worktree，不要两边在同一目录改同一份文件。

| 工作线 | 建议范围 | 要协调的边界 |
| --- | --- | --- |
| 编年史内容 | `technology-tree-data.json`、证据记录、历史正文 | JSON 建议同一时段只有一个编辑者；先商定新增 ID 和分类 |
| 学习台体验 | `prep-workspace*`、`prep-schedule*`、路线数据及相关测试 | 不改存储格式来省事；新行为先补兼容测试 |
| 审核工具 | `review_assist.py`、agent 文档和测试 | 默认无网络；任何远端运行单独确认 |
| 集成与验收 | `build.py`、`nav.toml`、全站 CSS、内容版次和 CODEOWNERS | 这些共享文件由集成人合并；不要双方各自重排 |

每个小 PR 说明：改了什么、为什么、实际跑了什么、没有验证什么。图与内容同时改时分开验收，不把“更好看”算成史料更完整。保持中英文事实一致，但不逐字翻译。

给接手者的起步任务：先读本文件和对应模块文档，再看完整 diff。第一批建议聚焦编年史内容，交付几篇明显比现有节点更好读的样例，再按这个质量扩展。不要先重写整个前端，也不要宣称已囊括所有 AI 历史。

## 5. 本地运行与验收

从仓库根目录运行；依赖沿用 `.github/workflows/site.yml`：

```sh
python -m pip install markdown pygments numpy
python site/collaboration.py
python -m unittest discover -s site/tests
python site/leakcheck.py
python site/paritycheck.py --strict
python site/build.py
git diff --check
python -m http.server 8797 --directory _site
```

`8797` 只是建议的隔离测试端口，若已占用请换一个。构建会重建 `_site`，不要在半成品目录里做链接验收。可选 PyTorch 测试可能跳过；记录实际测试数和跳过项，不声称做了 GPU 验证。

浏览器至少走两条完整路径：

1. 路线 → 修改日期 / 分钟 → 取消一次 → 确认保存 → 原文 → 返回学习台 → 导出 → 在隔离 origin 导入并核对。再查无存储权限、旧备份、未知记录和刷新行为。
2. 世界树 → 领域 → 年代 → 节点 → 关联节点 → 返回 → 切语言 → 刷新 / 浏览器后退。查手机、桌面、深浅主题、键盘和减少动效。

不要用读者实际进度做测试，不上传备份、私人参考资料或本地审核输入。小红书草稿不属于这次站点更新。PR 只负责保存和讨论当前进度；合并、Pages 部署、正式 Release 需另行确认，流程见 [RELEASING.md](RELEASING.md)。
